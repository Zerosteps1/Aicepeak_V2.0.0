# ADR-0008: Branch model with validation and production branches

- Status: Accepted by the maintainer on 2026-11-02 ([FACTORY-008](../work/FACTORY-008.md)); delivered locally outside the factory pipeline (decision 12)
- Date: 2026-11-02
- Deciders: Felix (`ftrutschnig`)
- Amends: [ADR-0007](0007-factory-cli.md) (decisions 1 and 3: the control checkout follows a listed branch, policy comes from the config branch)
- Related: [branch diagram](../factory-branches.md), [factory command reference](../factory-cli.md), [way of working](../way-of-working.md), [GitHub setup](../../factory/github.md)

## Context

Until now one branch, `main`, was at once the gated PR base, the trusted policy, the merge target and the only branch the factory CLI ran from. The maintainers want changes to travel in three levels: feature branches are gated automatically into protected validation branches, and only validated, deliberately promoted states reach protected production branches. The levels and gates must be configurable with the factory CLI, and the rules must still come from exactly one trusted place.

## Decision

1. **Three levels.** Feature branch → validation branch → production branch. A validation branch has a `gate`: `full` (deterministic tests, binding Astra review, automatic corrections), `tests` (deterministic tests only) or `none` (not gated). It also lists the work-order kinds routed to it; every kind (`factory`, `product`, `smoke`) is routed to exactly one validation branch. A production branch has a `review` mode for promotions: `no`, `initiated` or `maintainer-manual`.
2. **Names.** Today's `main` is renamed to `testing`: validation, gate `full`, all kinds, GitHub default branch. A new branch `production` (review `maintainer-manual`) is the production branch and the config branch.
3. **One config branch holds the rules.** `config_branch` in `factory/config.json` names a production branch (default: the only one). Gate code, configuration, policy and work orders always come from its tip: every `factory.yml` and `factory-promotion.yml` job is dispatched on it and refuses to run anywhere else, `session.py` runs from a disposable checkout of it, and the `factory-control` and `factory-promotion` environments and the WIF rule are limited to it. A finished change of the config branch is followed exactly once: when the old config branch names another listed production branch whose own configuration names itself, the dispatcher, the installer and the CLI use that branch (`branches.follow`).
4. **The branch list lives in the configuration.** `branches` in `factory/config.json` on the config branch lists the validation and production branches; `tools/factory/branches.py` validates it and every component reads it from there. `factory add validation branch`, `factory add production branch`, `factory remove branch` and `factory set config branch` change it through a config PR into the config branch that changes only `factory/config.json`; `set config branch` first opens the same change into the new config branch; it refuses while the new branch's configuration or work orders differ from the current config branch's, or while the default branch still names an earlier config branch, and `remove branch` refuses the branch the default branch still names as config branch. Config PRs open without an advisory preflight: maintainer approvals and `factory/deterministic` decide them, and the trusted tests run against the changed configuration. The config and default branches cannot be removed.
5. **Work orders start on the config branch.** `factory submit workorders` opens its PR into the config branch, so numbers stay unique. `factory sync workorder <n>` and `factory sync workorders` then push missing work orders unchanged to every validation branch; they never modify or delete files.
6. **Pushes.** Maintainers may push directly to validation branches. Nobody pushes directly to production branches; the rulesets have no bypass actors there. Who may bypass follows from the level alone, so the former setting `maintainer_check_bypass` (maintainers as `pull_request`-mode bypass actors of the single quality ruleset, Gabriel's merge rule of 2026-10-28 in `factory/evidence.md`) is removed: on validation branches maintainers keep merging and bypassing, on production branches nobody bypasses.
7. **Three kinds of PR into a production branch**, judged by the check `factory/production/<branch>`:
   - (a) **Promotion**: the head is a validation branch. It passes only when the head is the current tip of that validation branch, whose gate is not `none`; the production tip is already contained in it; it is the only open promotion into that production branch; and, with review mode `maintainer-manual`, a passed `factory/senior-review` exists for this PR, head, target and config tip. Otherwise it fails until `/bypass`.
   - (b) **Work-order or config PR**: it changes only `docs/work/*.md` and/or `factory/config.json`. It passes only with approving reviews at the current head by as many different maintainer accounts as `work_order_approvals` in `factory/config.json` names (2 when absent; set to 1 by maintainer decision of 2026-11-06, so for now one approval besides the author suffices); it never needs an AI review (`/review` is refused), and `/bypass` never applies. The check runs again after every review, dismissals included.
   - (c) **Anything else** fails and cannot be bypassed.
8. **Promotion.** `factory promote <V>` merges the production branch into `V` in the candidate when it is not yet contained (merge commit, never pushed; on conflicts the maintainer resolves them and pushes to `V`). Once production is contained, it opens the PR `V` → production, refusing while a promotion from another validation branch into that production branch is open; an open promotion of `V` itself simply carries the new head. It never merges; maintainers merge production PRs on GitHub with squash or rebase.
9. **Checks on PRs into production.** `factory/deterministic` runs on every new head with the config branch's rules. The AI review (`factory/senior-review`) starts only when a maintainer comments `/review`, never because of a new commit, and is reviewed on a maintainer device as before (ADR-0005). With `review` `maintainer-manual` it is required before merge, enforced by `factory/production/<branch>` (decision 7) rather than as a GitHub required check: GitHub matches required checks per commit, so a review published for another PR on the same commit would otherwise count. When the review finishes, the maintainer device re-runs the production check. With `initiated` it is optional; with `no` it is never offered.
10. **`/bypass <reason>`.** A maintainer comment on any factory PR, except type (b) above, publishes the required factory checks of the current head as passed by bypass. The check records the maintainer's login and the reason. A command counts only from an unedited comment and for the head the dispatcher saw when it was posted; a bypass is refused for a head whose commit is newer than the comment, runs only when dispatched by the dispatcher or the comment's author, is never reused by a job re-run or a dispatcher re-run, and survives a re-run of a gate-`tests` or production PR for the same head (a gate-`full` re-run is a new review). `factory merge` counts it only while its comment is unedited. A new commit, or a moved config tip, needs a new bypass.
11. **Binding.** Every factory check is bound to repository, PR, head, config tip, target branch, run and attempt (`contracts.binding`, 7 fields). A changed head, target branch, target tip or config tip makes a run stale. Bindings of the earlier 6-field form no longer count, so open PRs need a fresh run after the switch. A push to the config branch re-dispatches the open PRs into gated validation branches and other production branches; for `full` gates this means a new AI review, as a merge into the target branch always did.
12. **The CLI follows a listed branch.** The control checkout runs the code of the branch set with `factory use branch <n>`: by default the config branch, otherwise only a listed production or validation branch. The rules still come from the config branch, and the CLI always acts on the candidate checkout, whatever the current directory. `factory branches [--show]` writes the generated diagram `docs/factory-branches.md` (Mermaid) and with `--show` also opens it as a self-contained HTML page.
13. **Delivered locally outside the factory pipeline.** By maintainer decision of 2026-11-02, FACTORY-008 is implemented locally on its own branch, like FACTORY-007. The maintainer reviews the diff and decides how it lands; the owner then performs the runbook below.
14. **Revised after the independent review (2026-11-02).** An independent four-dimension review with adversarial verification found the gaps that decisions 3, 4, 7, 8, 9, 10 and 11 now close: the production AI review inside the production check, re-runs on a moved config tip, head-bound commands, re-checks on dismissed approvals and a config-branch change the factory can follow.

## Owner runbook (after the merge)

1. Freeze merges; make sure no merge lock exists.
2. Land the change into `main`.
3. Remove the `main` deployment-branch policy of `factory-control`. Rename `main` to `testing` on GitHub and confirm it is the default branch.
4. Create `production` from the tip of `testing`.
5. Run `python3 tools/factory/settings.py diff`, then `apply` (rulesets; environment policies before secrets). Add the publisher App key to the new `factory-promotion` environment.
6. Change the WIF rule `aicepeak-factory-author` so that `ref` and `workflow_ref` name `refs/heads/production` (the exact values are printed by `settings.py`), then run the WIF smoke on `production`.
7. On every maintainer device: reinstall the factory CLI.
8. Smoke test and record the results in [factory/evidence.md](../../factory/evidence.md):
   - a feature PR into `testing` (gate, `factory merge`);
   - `factory promote testing`; deterministic tests; `/review`; the production check; merge on GitHub;
   - a work-order PR with its maintainer approvals; `factory sync workorders`.

## Consequences

- The config branch receives only promotions and work-order/config PRs approved by maintainers (`work_order_approvals`). Nobody pushes to it, and `/bypass` never applies to its work-order and config PRs.
- A validation branch's content counts as validated once it is promoted, including commits that maintainers pushed directly. The promotion PR still runs the deterministic tests and, as configured, the AI review.
- Every `/bypass` is visible in the published check with login and reason, per head.
- The dispatcher runs the default branch's code (and, for pushes, the pushed branch's code). It only reads metadata and dispatches config-branch workflows, which re-verify every input.
- Residual risks: the branch list is trusted as declared; the CLI does not compare it with the GitHub rulesets. Two maintainer accounts are treated as two people. Until the owner runbook is complete, devices and open PRs are blocked (rename, WIF rule, fresh runs). Production rulesets require no approvals and restrict no updates, so any account with write access may click merge on a green production PR; today those are exactly the maintainers. `factory/deterministic` is still matched per commit: right after a promotion opens, a pass (or bypass) published for another PR on the same commit counts until the promotion's own run replaces it. A bypass comment's author can deliberately dispatch it again for a head that is older than the comment. The head is the one the dispatcher reads seconds after the comment, and "older than the comment" uses the commit's committer date: a commit made before a `/bypass` but pushed within that latency is covered by it, and so is a dispatch from workflow code a maintainer writes on a pushed branch (its `GITHUB_TOKEN` looks like the dispatcher). After a config-branch switch nothing re-runs open PRs until the next push to the new config branch or the owner's re-run step. Between merging a config-branch change and applying the settings for the new branch, factory jobs fail at the environment. `docs/factory-branches.md` is generated; config PRs cannot change it, so it is regenerated with `factory branches` in a later change.
