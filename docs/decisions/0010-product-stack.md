# ADR-0010: Product stack — C# backend, PostgreSQL, React frontend, Amazon Bedrock

- Status: Accepted by the maintainer on 2026-11-09; delivered locally outside the factory pipeline (decision 14)
- Date: 2026-11-09
- Deciders: Felix (`ftrutschnig`)
- Supersedes: AD-03 (Python 3.12+, FastAPI, Pydantic, SQLAlchemy/Alembic) of the former non-binding architecture proposal v0.4, which is removed with this decision
- Related: [north star](../../AICEPEAK_NORDSTERN.md) (AIC-06, AIC-12, §7), [architecture](../architecture/AICEPEAK_ARCHITECTURE.md), [ADR-0006](0006-northstar-approval.md)

## Context

The north star left the technology stack open (§7). Aicepeak is written mainly by AI agents in the software factory and reviewed by the maintainers, so the stack has to give agents fast, reliable error feedback and keep the code reviewable and cheap to maintain. The backend must:

1. call LLMs through Amazon Bedrock, the LLM provider the maintainers chose;
2. read and write a SQL database;
3. host the product's Web API;
4. run as a container image;
5. export Excel workbooks (moving this to Python is acceptable);
6. forecast individual line items with Bayesian regression and/or TimesFM, each followed by a Monte Carlo simulation that yields probability intervals (north star AIC-06); which method applies to which line items is open;
7. let users log in with Microsoft Entra ID.

The browser client is written in TypeScript with React, as the maintainers chose. For the backend, the maintainers compared C# with EF Core, Dapper or NHibernate, Node.js with Sequelize v6, and Python with FastAPI, SQLAlchemy and Alembic, using vendor documentation, release data, published benchmarks and community experience (sources below).

| Option | Outcome and main reason |
|---|---|
| C# + ASP.NET Core + EF Core | **Chosen.** The compiler checks API, data access and queries; ASP.NET Core ships OpenAPI, validation, authentication and background services; .NET 10 is supported until 14 Nov 2028; exact `decimal` type; among the fastest web stacks. |
| C# + Dapper only | Not the default: explicit, fast SQL, but SQL errors surface only at runtime and migrations, mapping and transactions are hand-built. Allowed for hand-tuned queries (decision 3). |
| C# + NHibernate | Rejected: smallest community and the least recent material for agents, steepest setup, slow release cadence, no advantage for a new product. |
| Node.js + Sequelize v6 | Rejected: a maintainer called maintenance "not very active" (July 2026), v7 has been in alpha for years, weak TypeScript types, no decimal type in JavaScript, and agents mix its many API versions. |
| Python + FastAPI + SQLAlchemy | Rejected as the main backend: type checking is optional, FastAPI is still 0.x and allows breaking changes in minor versions, Microsoft ships no official library for validating Entra tokens in a Python API, and it is slower. Its real advantage, the statistics and ML ecosystem, would only be needed for TimesFM, which is not yet adopted. |

Bayesian regression does not require Python: the conjugate (closed-form) model is plain matrix algebra, and Infer.NET covers more complex models deterministically. Only MCMC sampling (NUTS) lacks a mature .NET library. TimesFM, if it is adopted, would be the one hard Python dependency, and it would belong in its own container in any stack (about 0.9 GB of fp32 weights for version 2.5, separate memory and scaling).

## Decision

1. **Language and runtime.** C# on .NET 10 (LTS, supported until 14 Nov 2028). Upgrades follow the next LTS release.
2. **Web API and browser client.** ASP.NET Core with its built-in OpenAPI document (3.1), request validation and health checks. The browser client is written in TypeScript with React and uses only this API.
3. **Data access.** EF Core is the default. EF Core generates migrations from the model; they are reviewed like code. Dapper is allowed for hand-tuned read or reporting queries on the same connection, each covered by a test against a real PostgreSQL database (decision 11). NHibernate is not used.
4. **Login.** Microsoft Entra ID. The API validates Entra access tokens with Microsoft.Identity.Web and authorizes with Entra app roles or scopes; the React client signs users in and obtains tokens with MSAL React (`@azure/msal-react`, authorization code flow with PKCE). The backend identifies a user by the token's tenant ID (`tid`) and object ID (`oid`), which Microsoft documents as immutable and usable as a database key; the database stores them as ordinary columns, so login does not depend on the database engine. Whether customers log in from their own Entra tenants (multi-tenant app registration) or from a single tenant is open.
5. **LLM access.** Through Amazon Bedrock, called only from the backend with the AWS SDK for .NET v4 (`AWSSDK.BedrockRuntime`) and its Converse API, which uses one request format for all models on Bedrock (v3 of the SDK has reached end of support). Which models on Bedrock are used is chosen separately.
6. **Forecast engine in C#.** Bayesian regression per line item (closed-form conjugate model with Math.NET Numerics; Infer.NET only where a model needs it), the Monte Carlo simulation and the probability intervals run in the backend. Interval limits are percentiles of the Monte Carlo results; Math.NET's `StudentT.InvCDF`, which its documentation calls slow and unreliable, is not used for them.
7. **Reproducible Monte Carlo.** One fixed, seedable generator algorithm is used, not `System.Random`, whose seeded sequence Microsoft does not guarantee across .NET versions and which is not thread-safe. Every path or batch gets a seed derived from the run's seed, results are combined in a fixed order, and a test shows that the same seed gives byte-identical results with any number of threads. Math.NET Numerics is pinned; its last stable release is 5.0.0 from April 2022.
8. **TimesFM: intended per line item, not yet adopted.** The north star names TimesFM as an alternative or addition to Bayesian regression for individual line items; whether and for which line items it is used is open. Until it is adopted, the backend has no Python component. If it is adopted, it runs in its own Python container with Google's official `timesfm` package and TimesFM 2.5 (weights Apache-2.0). Self-hosted TimesFM 3.0 would be excluded: its weights allow no commercial or production use outside authorized Google Cloud services. The container would expose one internal endpoint (history in; mean and 10th to 90th percentiles per period out), be reachable only from the backend, hold no user credentials and contain no business logic. Its package versions would be pinned, with tests comparing its output with stored known-good results, and every forecast run would store the TimesFM output it used, so a rerun never depends on the model returning identical numbers.
9. **If TimesFM is adopted: from its percentiles to Monte Carlo.** TimesFM returns separate percentiles per period, not simulated paths, and nothing outside the 10th to 90th percentiles. How periods and line items would move together in the simulation, and how intervals wider than 10 to 90 would be justified, are then open methodology decisions. Backtesting checks how often actuals fall inside the intervals, whatever the method.
10. **Excel export.** In C# with ClosedXML (MIT). EPPlus is not used: commercial use needs a paid licence since version 5. Moving the export to Python remains allowed.
11. **Database: PostgreSQL.** EF Core uses the Npgsql provider (`Npgsql.EntityFrameworkCore.PostgreSQL`, 10.x for EF Core 10). Reasons: no licence cost, a managed service on every major cloud while hosting is open, and a provider that keeps pace with EF Core (10.0.0 shipped on 22 Nov 2025). Validity periods (for example "this price applies from January to June") use PostgreSQL range types, which Npgsql maps and translates in LINQ. Keys that reject overlapping periods need PostgreSQL 18 and version 11 of the Npgsql provider. Time series use ordinary tables, partitioned by date if volumes require it; TimescaleDB is not assumed, because managed clouds offer it only partly or not at all. PostgreSQL has no built-in automatic history of row changes: a forecast run's reproducibility already rests on its stored inputs and outputs, and an audit trail of data edits, if needed, is built with triggers. The PostgreSQL major version is chosen with the hosting. Not chosen: SQL Server / Azure SQL, whose built-in change history and Microsoft-maintained provider do not outweigh licence costs and the tie to Azure. Also not chosen: MySQL and MariaDB (Pomelo's provider has no EF Core 10 release), document databases, and SQLite (tests only).
12. **Containers.** The backend ships as a container image, and so would a TimesFM service if it is adopted. Hosting and cloud provider are open.
13. **Revisit trigger.** If Python becomes necessary for more than TimesFM inference (for example MCMC sampling with PyMC, or scikit-learn or statsmodels models as business logic), this decision is reassessed, including an all-Python backend.
14. **Delivered locally outside the factory pipeline.** The change touches protected paths (decision records, README, north star) that the isolated author cannot write. The maintainer reviews the diff and decides how it reaches `testing`.

## Consequences

- API, data access, business logic and the forecast engine share one compiler-checked language. The browser client adds TypeScript, which brings its own compiler checks. Python appears only if TimesFM is adopted, and then only in one small container that needs its own lint, type check and tests in CI.
- Product checks for the .NET build and tests, the TypeScript build and tests of the browser client (and, if TimesFM is adopted, its container) do not exist yet; `product_checks_ready` stays `false` until they do.
- Math.NET Numerics is barely maintained. Only its mature parts (linear algebra, distributions, generators) are used, behind tests.
- The north star now requires probability intervals computed by Monte Carlo simulation (AIC-06) and Entra login (AIC-12), and describes the forecasting approach: Bayesian regression and/or TimesFM per line item, each with Monte Carlo simulation (AIC-06). §7 leaves open which method applies to which line items and points to this record. ADR-0006 recorded the approval of the earlier north-star text; the changed sections still need the maintainers' review (north star §8).
- The former architecture proposal v0.4 and its validation report are removed (they remain in the Git history). That proposal traced requirements AIC-001 to AIC-055 of an earlier north-star version. Its other topics (editions, tenancy, security, compliance, operations) are no longer documented and need their own decisions when they become relevant.
- Open: which line items use Bayesian regression, TimesFM or both (decisions 6 and 8) and, if TimesFM is adopted, how its output feeds the Monte Carlo simulation (decision 9); the Entra tenant model (decision 4); hosting and cloud (and with it the PostgreSQL major version); which models on Amazon Bedrock are used (decision 5); and whether data edits need an audit trail (decision 11).
