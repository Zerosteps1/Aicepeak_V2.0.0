Run them from a clean checkout of the config branch: the branch list, gates and review modes come from its `factory/config.json`. `codeowners` checks login, numeric ID and write permission through GitHub and writes the local CODEOWNERS file, which is merged through a PR. `inspect` and `diff` are read-only. `apply` changes only the managed settings, refuses known blockers and reads the state back. Managed are the rulesets named by `ruleset_names` (one per listed branch and the lifecycle ruleset) and rulesets of branches no longer listed; `apply` creates or updates the wanted rulesets first and deletes the others only afterwards. Other rulesets stay in place. `wif` prints, without network, the claims the federation rule must match for the config branch (`ref`, `workflow_ref`, environment, event). Apps, secrets, branches, plans and merges are never set up automatically.

Blockers include: a listed branch that does not exist yet (the lifecycle ruleset would forbid creating it), `factory-promotion` holding any secret other than the publisher key, factory credentials stored as repository secrets, `.github/CODEOWNERS`, `factory.yml`, `factory-dispatch.yml`, `factory-promotion.yml` or `factory-feedback.yml` missing on the config branch or the default branch, a CODEOWNERS file there that differs from the verified owners, a live default branch other than `default_branch`, and an invalid branch model.

`inspect`, `diff` and `apply` also print `wif_claim` and `owner_steps`, the steps only the repository owner can take, in order: create each missing listed branch on GitHub before `apply`; review `diff`, then run `apply` (environment branch policies are set before any secret is added); after `inspect` shows an environment limited to the config branch, add its missing secrets; set the federation rule to the printed `ref` and `workflow_ref` and run `gh workflow run factory.yml --ref production -f pr=0 -f wif_smoke=true`.

Administration needs a separately authenticated human `gh` identity. The automation creates its own short-lived installation tokens, limited to the target repository and the permissions it needs. ## Enforcement after activation

`settings.py` derives one ruleset per listed branch and one lifecycle ruleset from the branch model ([branch diagram](../docs/factory-branches.md), generated by `factory branches`; a config PR changes only `factory/config.json`, so the diagram is regenerated in a later change):

1. **Validation branches** (`Factory validation: <branch>`, today `testing`): the `update` rule (only bypass actors may update the branch), PR required with resolved review threads and stale approvals dismissed on push, and the required checks of the branch's gate (`full`: `factory/deterministic` and `factory/senior-review`; `tests`: `factory/deterministic`; `none`: none), each up to date with the branch and bound to the expected publisher `integration_id` (see [required checks](#required-checks-and-activation)). The approved setting `require_second_human_review: false` requires zero approving reviews, no mandatory Codeowner approval and no separate last-push approval. Every verified maintainer account is a bypass actor with mode `always`: maintainers may push directly and merge; `factory merge` merges with `--admin` only after verifying the checks itself. GitHub records every bypass; Apps and bots never get one.
2. **Production branches** (`Factory production: <branch>`, today `production`): PR required with the same review parameters, merge commits only (`production_merge_methods: ["merge"]` in `factory/github-settings.json`; `settings.py` refuses any other value: squash and rebase write commits that no validation branch contains, a merge commit keeps the validation branch's commits so that `factory update` brings production back as a fast-forward), and exactly the required checks `factory/deterministic` and `factory/production/<branch>`, up to date and App-bound. There are **no bypass actors**: nobody pushes directly, and a PR merges on GitHub only when every required check passed. The maintainer approvals of a work-order or config PR (`work_order_approvals`, today 1) and, for review mode `maintainer-manual`, the passed AI review of a promotion are enforced by `factory/production/<branch>`, not by GitHub's review count or a required `factory/senior-review`: GitHub matches required checks per commit, so a review published for another PR on the same commit would otherwise count.
3. **Branch lifecycle** (`Factory branch lifecycle`): no one may create, delete or force-push a listed branch or the reserved names `main`, `master` and `head`. A new listed branch must therefore exist before `apply`, and after the rename nobody recreates `main`.

Who may bypass follows from the level alone: maintainers always bypass validation branches, and production branches have no bypass actors (the former `maintainer_check_bypass` setting was removed with ADR-0008). A recorded exception for exactly one head is the factory's `/bypass` (see [below](#executable-review-and-fix-flow)), which never applies to work-order or config PRs into a production branch.

The combination follows the documented [aggregation of rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#about-rule-layering). Real negative probes remain necessary. Administrators can always change settings; the factory does not claim immutability against the repository administrator. [Rulesets API](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset), [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)

## Executable review and fix flow

`factory-dispatch.yml` handles PR creation, new commits, reopening, ready/draft, edits, human PR comments, maintainer commands on work-order issues and pushes to listed branches. For `pull_request_target`, `issue_comment` and `workflow_run` it runs the default branch's code; for a push, the pushed branch's copy (listed names contain no `/`, so its `branches: ['*']` filter never matches tags). It reads the name of the config branch from its own checkout and `factory/config.json` at that branch's tip through the API. When that configuration names another listed production branch whose own configuration names itself (a finished `factory set config branch`), it follows that one hop (`branches.follow`); any other mismatch refuses to dispatch. It routes only with the followed configuration, whose tip is the policy. It dispatches `factory.yml` and `factory-promotion.yml` only with `ref` set to the config branch; those re-verify every input. For reviews and inline comments, `factory-feedback.yml` provides only numeric references, without permissions, checkout or secrets. The trusted `workflow_run` dispatcher reads run, workflow, human author and PR association again from GitHub. Manipulated titles or comments formatted the same way are no authorization. A comment on an issue (not a PR) is dispatched only when a configured maintainer created it (not edited), it starts with `/review` or `/accept`, the issue was opened by a configured maintainer, the run is attempt 1 and the config branch's configuration has `issue_review_model`; then `factory.yml` gets the inputs `issue`, `issue_command` and `comment`, never the comment text. [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [secure pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

Routing by the PR's target branch (only configured maintainers' comments and reviews count; an edited `/review` or `/bypass` comment is ignored, only a newly created one acts, and the dispatch carries the PR head it read as input `head`):

| Event | Validation branch, gate `full` | Gate `tests` | Gate `none` or unlisted | Production branch |
|---|---|---|---|---|
| PR opened, new commit, reopened, ready/draft, edited | `factory.yml` | `factory.yml` | nothing | `factory.yml` (deterministic) and `factory-promotion.yml` |
| Push to the target branch | `factory.yml` for its open PRs whose base is the pushed tip | same | nothing | `factory-promotion.yml` for its open PRs |
| Push to the config branch, in addition | `factory.yml` for every open PR (no base-tip skip: its base did not move) | same | nothing | other production branches: `factory.yml` and `factory-promotion.yml` for every open PR |
| Comment `/review` | ordinary feedback | nothing | nothing | `factory.yml` with `review_request` and `head` (review mode not `no`; the job refuses work-order/config PRs) |
| Comment `/bypass <reason>` | `factory.yml` with `bypass` and `head` | same | nothing | `factory.yml` and `factory-promotion.yml` with `bypass` and `head` |
| Other comment | feedback run | nothing | nothing | nothing |
| Review or inline comment | feedback run | nothing | nothing | `factory-promotion.yml` (approvals) |
| Dismissed review | `factory.yml` (plain update, no feedback forwarded) | nothing | nothing | `factory-promotion.yml` (approvals) |

Each PR is dispatched once per event. `factory-feedback.yml` reports submitted, edited and dismissed reviews; for a dismissal the dispatcher requires only that the run actor (the dismissing account) is a configured maintainer, since the review's author did not act. On a gate `full` PR a dismissal changes the feedback a pending senior review is bound to, so the plain pipeline update takes a fresh snapshot. A re-run of a dispatcher run (attempt other than 1) for a `/review` or `/bypass` comment fails with "a re-run never repeats a command; post a new comment": it would replay the old comment against the head as it is now. Other events dispatch on re-runs as usual.

`factory.yml` runs only through `workflow_dispatch` on the config branch: every stage first verifies `GITHUB_REF` against `config_branch` from its own checkout, so its code, configuration and policy are the config tip (work orders are pinned issue texts), and `factory-control` admits no other branch. A normal run is **snapshot → tests → publish**: `Snapshot` binds the PR (into a gated validation branch from a feature branch, or into a production branch) and, for gate `full` only, reserves the `factory/senior-review` check; `Deterministic tests` runs secret-free in the trusted [test image](clients.md#test-image): the factory checks and the product steps ([ADR-0011](../docs/decisions/0011-product-checks.md)), each sandboxed, with every test case in the run's job summary. `Publish gates` creates `factory/deterministic` with the step table and annotations at failing tests and compiler/lint errors. No job calls a model and no job holds a model credential for review. Native dispatch job checks are not used as PR gates; the publisher App creates the separate factory checks on the checked PR head. [Required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [Checks API](https://docs.github.com/en/rest/checks/runs)

When the deterministic checks of a gate `full` PR pass, `Publish gates` leaves `factory/senior-review` **in progress** ("Awaiting senior review") with a pending receipt: phase `awaiting_review`, the authenticated snapshot (repository, PR, head, target branch and its tip, config tip, run ID and attempt, files, work order, feedback digest, draft and control-change flags) and the test evidence. The check summary names the command for the maintainer. When the checks fail, the PR is a draft or the snapshot is stale, both checks are completed as `failure` and no review is requested; the PR is labeled `needs-author-action` unless it is a draft or only the config tip moved (`stale policy`: the dispatcher re-runs it on the new tip). For gate `tests`, `Publish gates` publishes only `factory/deterministic`; no review is reserved and no correction starts. When a gate `tests` or production re-run of a head fails but a valid `/bypass` of `factory/deterministic` for this head, PR, target and config tip exists, the failure is not published, the PR comment says that the bypass stays for this head, and `needs-author-action` is removed. If a newer publisher run on the commit hides that bypass (another PR on the same head, or a failure published after a lookup error), the re-run publishes the bypass record again, bound to its own run (title `Bypassed by <login>`, summary `Reason: <reason>`, the receipt as text), so that it is the newest run; the comment adds "it was published again as the newest run". When the only authentic bypass of this head, PR and target was made for an earlier config tip, the failure is published, the comment says "the `/bypass` by <login> was for an earlier config tip; post a new `/bypass`", and no `needs-author-action` follows. The pipeline comment of a work-order/config PR says that the senior review is not used for it and that maintainer approvals decide it. `Publish gates` also requires the PR head to contain the current tip of its target branch (compare API, `behind_by` 0). GitHub moves a PR's base SHA on every push even when the target was not merged into the branch (PRs #4 and #5), so base equality alone does not prove that the tested head is what a merge produces; such a head fails with the hint to use "Update branch". Because every maintainer merge into a validation branch uses the ruleset bypass, which skips GitHub's own up-to-date and check rules, `session.py merge` re-verifies head, the current target and config tips, the App-bound checks of the gate (or authentic `/bypass` checks), the reviewed handoff and feedback, and open threads. Because GitHub's merge pins only the head, it serializes merges into each branch with the lock `refs/tags/factory-merge-lock--<branch>` (ref creation is atomic; an existing ref is refused), re-reads the tips and the PR while holding it, and checks the merge commit's parents afterwards. The dispatcher never sees the lock: its push trigger matches only branches. `session.py merge` refuses PRs into production branches, which maintainers merge on GitHub. The maintainer-local reviewer `python3 tools/factory/local_review.py --pr N` requests an exclusive claim through the serialized `factory.yml` on the config branch, then submits a separate neutral result record. Only that workflow finalizes the gate; see [Clients](clients.md#senior-reviewer-maintainer-local).

**PRs into a production branch.** The snapshot carries no handoff and no work-order scope; `factory/deterministic` runs the config branch's trusted tests against every new head, and `limits.max_changed_files` binds only a requested review. On a config PR the head's `factory/config.json` carries a changed branch list or config branch; the trusted tests never take the branch model from it (they use a fixed one of their own and only check that the changed one is valid), so such a change does not fail them. Engine and production check classify a PR into a production branch with one helper (`bypass.production_kind`): a **promotion** when its head is a validation branch of this repository, otherwise a **work-order/config PR** when every path, rename sources included, is `docs/work/*.md` or `factory/config.json`, otherwise **other**. `factory/senior-review` exists only after a maintainer's `/review`: the `Review request` job (inputs `review_request`, the comment ID, and `head`, the PR head the dispatcher read; job reruns refused) verifies that the comment is an unedited `/review` by a configured maintainer on this open PR into a production branch whose review mode is not `no`, that the PR is not a config PR ("config PRs need no AI review: maintainer approvals decide them"), that `head` is still the PR's head (before and after the snapshot), that the PR is ready and that `factory/deterministic` passed for that head with the current config tip, and then reserves the senior review for exactly that head; a maintainer device reviews it as above, against the diff from the production tip to the head. A new commit never re-reserves it; comment `/review` again. Later maintainer feedback, a moved config tip or a moved target tip makes the pending review stale (a reservation for an older target tip is never claimed); `session.py watch` then returns status `stale` instead of waiting, with "feedback or the config branch changed after /review; comment /review again" or, when the target moved (into the config branch it moves with the config tip), "the target branch moved after /review: update the promotion (`factory promote <V>`), then comment /review again" (`--to <P>` added when several production branches are listed). With review mode `maintainer-manual` the production check of a promotion requires the passed review (below), with `initiated` it is advisory, and work-order/config PRs never need it. When a production review finishes, `local_review.py` re-runs the production check with the maintainer's own `gh` (`gh workflow run factory-promotion.yml --repo Zerosteps1/Aicepeak_V2.0.0 --ref <config branch> -f pr=<n>`); if that dispatch fails, the review stands and the command is printed. When the process ends before that (the result dispatch failed, the wait for the coordination timed out, or it was interrupted), its `Blocked` message names the same command, to run once the review is complete.

**Work-order issues** ([ADR-0009](../docs/decisions/0009-issues-as-work-orders.md)). A dispatch with `issue` set runs only the issue jobs; every PR job requires `issue` `0`, and every issue job `pr` `0`. The concurrency group is `issue-<N>` (GitHub keeps one pending run per group). `Issue review` (`/review`; `contents: read`, `issues: read`, `id-token: write`, no App key) re-reads the issue and the command, refuses (as job output, without a model call) a closed issue, an invalid `factory-task` block or an exhausted `limits.max_issue_reviews`, lists the files of the validation branch routed for the work order's kind, calls `issue_review_model` once through the federation rule with a structured output and no tools, and validates the result (schema, the factory's path rules). `Issue review comments` (publisher key, no OIDC) verifies the command again, requires the reviewed title and description to be unchanged and posts the proposal and the findings as publisher-App records, or a notice when the review was refused or did not complete. `Issue accept` (`/accept`; publisher key) counts the unedited `/accept` comments of distinct maintainer accounts after the newest proposal, requires the issue unchanged since it, writes only the `factory-task` block (`status: approved`, the proposed paths), reads the issue back and posts the approval record bound to the read-back text; a refusal is posted as a comment and changes nothing. `tools/factory/issues.py` verifies these records for every consumer; `Deterministic tests`, `Author correction` and `Push correction` re-check a snapshot's pin with `issues: read`.

**`/bypass <reason>`.** The `Bypass` job (inputs `bypass`, the comment ID, and `head`; a reason of 1 to 500 characters; job reruns refused) verifies the maintainer comment and the open PR into a gated validation branch or a production branch, refuses a work-order/config PR into a production branch (classified as above, so every promotion is accepted, also one whose diff holds only work orders or `factory/config.json`), and publishes every required check of the target except `factory/production/<branch>` for the current head as `success`: title `Bypassed by <login>`, the reason as summary, the receipt `{"bypass": {"login", "id", "comment_id", "reason"}}` as text and the bypass run's binding as `external_id`. It refuses an edited comment (`created_at` differs from `updated_at`), a `head` that is not the PR's current head, a head whose commit (committer date) is newer than the comment, and a run that neither the dispatcher (`github-actions[bot]`) nor the comment's author started. On a promotion, `factory-promotion.yml` handles the production check for the same comment with the same checks and refuses any attempt other than 1. `session.py merge` and the production check accept a bypass only from the publisher App, for the current head, with a 7-field binding of the same PR, target branch and current config tip, naming a configured maintainer by ID and login; `session.py merge`, the production check and a kept bypass also re-read the comment, which must still be that maintainer's unedited `/bypass` on this PR (`session.py merge` otherwise reports "the `/bypass` comment was edited or deleted; post a new `/bypass`"). A re-run for the same head keeps it on gate `tests` and production PRs (see `Publish gates` above); a gate `full` re-run reviews again. On a PR into a gated validation branch the `Bypass` job removes `needs-author-action`. A new head needs a new `/bypass`.

**Production check.** `factory-promotion.yml` (environment `factory-promotion`, only the publisher key, `contents: read`) runs `tools/factory/promotion.py` on the config branch and publishes `factory/production/<branch>` on the PR head:

- (a) **promotion**, the head is a validation branch of this repository: success only when the head is that branch's current tip, its gate is not `none`, the production tip is contained in it and no other promotion into the production branch is open, and, for review mode `maintainer-manual`, the newest publisher `factory/senior-review` on the head bound to this PR, head, config tip and target is completed with `success` (otherwise: "the AI review of this head is missing: a maintainer comments `/review`", with the hint that a review that passed since needs only a re-run of this check and its `gh workflow run factory-promotion.yml` command, "awaiting the local AI review" or "the AI review did not pass"); otherwise failure naming the reasons (a production tip that is not contained names `factory promote <V>`, with `--to <P>` when several production branches are listed), unless a valid `/bypass` exists for exactly this head (an earlier one for the same head, PR, target and config tip keeps counting while its comment is unedited);
- (b) **work-order/config PR** (the other docs call it a config PR: work orders are GitHub issues, so only `factory/config.json` and the device smoke's file still go this way), not a promotion and every file and rename source is `docs/work/*.md` or `factory/config.json`: success only with approving reviews at the current head from as many different configured maintainer accounts as `work_order_approvals` in `factory/config.json` names (default 2 when absent, today 1) (the latest approval, change request or dismissal of each account counts; it runs again after every review, dismissals included); no AI review; `/bypass` never applies;
- (c) **anything else**: failure, no bypass.

Draft PRs fail. When the head, the target tip or the config tip moved during the run, it publishes nothing; the newer state gets its own run.

Every check binds `repository:PR:head:policy:base_ref:run:attempt` (`contracts.binding`) as its `external_id`: the config tip as policy and the target branch's name; the snapshot also records the target tip. A changed head, target branch, target tip or config tip makes a run stale; checks with the earlier 6-field binding never count, so open PRs need a fresh run after the switch. Because every check binds the config tip, a push to the config branch re-dispatches the open PRs into the gated validation branches and the other production branches (see the routing table; gate `full` PRs get a new AI review). After a change of the config branch, the merge into the old one is no longer such a push; the owner re-runs the open PRs on the new config branch (the last owner step of `factory set config branch`), or its first push does. `session.py merge` reports a check that differs only in the config tip as "the config branch moved after this run; a fresh run is dispatched automatically" and names the retry below as the fallback. Check evidence is verified against authenticated GitHub run, workflow and job data. Test orchestration comes from the config branch; candidate code runs in a container without network, secrets, home or Docker socket. The publisher accepts no success JSON from the PR. Incomplete, skipped, cancelled or contradictory evidence does not approve. [Run API](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run), [workflow context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)

Author work starts only from a separate correction dispatch for a published review:

```sh
gh workflow run factory.yml --ref production -f pr=123 -f correction=<check_id>
```

`local_review.py` sends this itself when a review requests changes and `automatic_correction` is `true`; a maintainer can also send it by hand. Every correction rechecks that this is still the latest authenticated review for the PR, including retries at the same commit. The run skips the snapshot and starts with the **Correction gate**, which refuses unless `automatic_correction` is `true` (the target configuration enables it; it takes effect only after the reviewed merge), the run is attempt 1, the triggering actor is a configured human maintainer, the check is an authentic, completed publisher `factory/senior-review` check of that PR with a valid `changes_requested` review, the PR targets a validation branch with gate `full` and changes no control paths, the run executes the reviewed policy revision, and head, target branch and its tip, config tip, handoff and feedback are still current. If the target or the config branch moved on after the review, the gate refuses; the next pipeline run and review come first. The gate then reserves an author round (`factory/author-reservation`, `limits.max_run_cost_usd`) bound to its own run ID.

The `Author correction` and `Push correction` jobs check that the reservation belongs to the current correction run. The allowlist runner gets no GitHub credentials. The writer checks run, artifact ID/digest, exactly one bounded patch, work order, allowed paths and current head, and pushes only to unlisted feature branches; it runs no artifact programs. Changes to control rules are excluded. An App push should trigger the next check run; this actual follow-up trigger is part of the still open smoke evidence. [Artifacts](https://docs.github.com/en/rest/actions/artifacts#get-an-artifact), [follow-up triggers](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)

Branch updates use the atomic [`updateRefs`](https://docs.github.com/en/graphql/reference/git#updaterefs) mutation with `beforeOid`, `afterOid` and `force:false`. This also rejects an intermediate reset to an ancestor. REST `force:false` alone would only check fast-forward. Source read; no real mutation executed yet.

## Feedback, retry and troubleshooting

Ordinary comments, reviews and inline comments of verified humans on a PR into a `full` validation branch are read again in the next run; on a PR into a production branch, reviews (dismissals included) re-run the production check, and human feedback is bound only where a requested review reads it; feedback after a `/review` makes that pending review stale, so a maintainer comments `/review` again. The review answers relevant questions; corrected or disputed findings receive the author report. New feedback invalidates old context. Human threads stay open until humans resolve them. An expanded scope first needs a new, approved work-order issue.

A PR-wide, App-authenticated ledger references real check records and keeps budgets and rounds across rebase and force push. At most two automatic corrections (`limits.max_rounds`) and at most `limits.max_reviews_per_pr` claimed senior review attempts per PR, including dry-runs and failed attempts. The same context must not be processed twice. GitHub serializes review ownership/publication and correction writers. Only authenticated runs for old heads, config tips or target branches are actively cancelled; pure title edits do not interrupt a valid run. A verified run on a former config branch is skipped, neither cancelled nor refused: it cannot act for the current config. Fresh state checks before every relevant stage, before publication and before the atomic push remain required as well. Provider requests that already started can incur costs until cancelled.

Without a new commit, a verified maintainer can deliberately start a new run:

```sh
gh workflow run factory.yml --ref production -f pr=123 -f retry=true
```

Replace `123` with the actual PR number. GitHub's "Re-run jobs" is refused so that old budget reservations are not reused. A retry resets neither rounds nor budget. Every new pipeline run leaves a new pending senior review; run `local_review.py --pr 123` again. With exhausted budget, conflicts, missing credentials or no progress: `needs-author-action` and the concrete launcher/skill path in the PR. No silent client switch.

Troubleshooting: first compare run/check ID and head, then the doctor and `settings.py inspect/diff`; check reviewer access separately with `python3 tools/factory/local_review.py --smoke` on the reviewer Mac. Rule changes, raised limits and lasting decisions need a PR and human approval. Never remove a protection rule to force a green result.
