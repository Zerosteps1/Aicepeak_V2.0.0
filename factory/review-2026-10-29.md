## Defects only the live run could find

The automatic correction path (review → Claude author → writer push) had never run end to end before 2026-10-28. Its unit tests mocked the transports. The live run on PR #10 exposed two defects in sequence. Both are fixed through reviewed PRs, with no gate exception:

1. **Author container could not write its work volume** (run [40762431387](https://github.com/Zerosteps1/Aicepeak_V2.0.0/actions/runs/40762431387), fixed in #17). When the second container mounts the shared tmpfs volume, Docker copies the image's `/work` owner (1000:1000) onto it. The seed, running as the host uid, gets `Permission denied`. Reproduced locally with plain `docker run`; fixed with `volume-nocopy`.
2. **Writer push used a GraphQL field that does not exist** (run [40766190552](https://github.com/Zerosteps1/Aicepeak_V2.0.0/actions/runs/40766190552), fixed in #18 + #19). `UpdateRefsInput` has `refUpdates`, not `updates`; the live API answered "Field is not defined". The unit test mocked the same wrong name. In that run the Claude author itself worked: it changed exactly the one line and wrote an accurate report.

Both runs failed closed: `needs-author-action`, no false success, budgets charged. A side effect of the policy's trusted base suite is that a defect encoded in a base test needs **two PRs**. The first makes the test accept the correct behaviour; the second fixes the code.

**Diagnosability (P1 recommendation).** The author step reports only `author runner failed or credentials missing` and discards the launcher's reason so that secrets cannot leak. Finding the cause took a local Docker reproduction. Recommendation: publish the launcher's fixed `reason` prefix (for example `docker failed (1)` and the failing stage name) without the free-text stderr.

## How the work actually flows

1. **Work order.** `docs/work/<ID>.md` with an approved `factory-task` block. It must be merged in its own PR first (handoff task FACTORY-001 allows `docs/work/`), because the factory reads tasks from the protected base. Template: [TEMPLATE](../docs/work/TEMPLATE.md).
2. **Implementation.** On a separate branch, ideally through `clients.py launch --runner claude` (isolated container). Then `session.py preflight` for an advisory Astra review and `session.py submit`, which opens the PR with the handoff.
3. **Gate.** The trusted pipeline runs deterministic tests and then waits. **No review happens until a maintainer runs `session.py watch --pr <n>`** on a machine with Codex token and publisher key. The `awaiting-senior-review` label (since #16) shows these PRs. Query: `gh pr list --label awaiting-senior-review`.
4. **Findings.** The publisher writes the summary as a PR comment and the structured findings into the check output. P0/P1 give `changes_requested`. For non-control paths the watcher dispatches an automatic correction: **Claude (Sonnet 5.5) in GitHub Actions via Workload Identity Federation**, pushed by the writer App, followed by new tests and a new review. Control paths (`.github/`, `factory/`, `tools/factory/`, `docs/work/`, README, …) are never auto-corrected; they get `needs-author-action`, and a human-driven session fixes them. P2 findings are not acted on automatically.
5. **Limits.** At most 2 automatic correction rounds, 6 claimed reviews and USD 25 author budget per PR. Exhausted limits, conflicts and missing credentials end in `needs-author-action`, never in a silent pass.
6. **Human feedback.** Comments and reviews by Gabriel or Felix are re-read and trigger a new snapshot and review. `session.py response --post` answers questions with citations. Threads are never auto-resolved.
7. **Merge.** Normally two green App-bound checks and resolved threads, then Gabriel or Felix merges, with no second approval. Since 2026-10-28 both may also merge a stuck PR through the ruleset bypass ("Merge without waiting for requirements"), which works only through the PR and is recorded by GitHub. They write the reason as a PR comment first. Agents and bots have no bypass.

**Claude is not a reviewer in the gate.** The only binding reviewer is GPT-6 Astra/high. "Claude review comments" in PRs do not exist; Claude appears as the correcting author (commit by the writer App) and as an optional local review role.

## Friction and recommendations (prioritized)

1. **P1 – Reviewer availability.** Reviews depend on someone running `watch`. If nobody can, the maintainer bypass is the escape hatch; use it sparingly, because a bypassed PR has no independent review. Recommendation: each maintainer runs `session.py watch --pr <n>` right after `submit` (`submit` already does this for ready PRs). Check `gh pr list --label awaiting-senior-review` once a day.
2. **P1 – Every merge invalidates all open PRs.** The snapshot requires PR base = current `main`. After a merge, every open PR needs "Update branch" plus a new review (a new review slot). The push-triggered dispatch after a merge always fails with `dispatch must run current protected base` (5 red runs at 19:25 UTC on 2026-10-28). Recommendation: keep few PRs open in parallel and merge in small steps. Later, let the push dispatcher skip PRs whose base is not the pushed SHA.
3. **P1 – Costs.** Automatic corrections are Anthropic API usage (Console workspace of the WIF federation), not the Claude Team subscription. Team API credits may cover them. Check balance and auto-reload in the Console. Budgets: USD 12 per run, USD 25 per PR.
4. **P2 – Repository is public.** North star, specification sheet and factory design are publicly readable. If that is not intended, a private repository needs a matching GitHub plan (see `factory/github.md`) and a check that rulesets and environments still apply.
5. **P2 – Language mix.** Policy, README and CONTRIBUTING are German; newer documents are English. This is not a functional problem, but the choice should be made once.
6. **P2 – Branch hygiene.** `delete_branch_on_merge` is off. The branches of merged PRs remain; none is linked from `main`. Recommendation: enable "Automatically delete head branches" in the repository settings and delete the merged branches once; they can be restored from each PR page. Keep the branches of closed PRs #4–#6 and #15 as records.

## Usability check: effort vs. benefit

Measured today on about 14 live pipeline and review cycles:

- A normal PR takes about **6–10 minutes** from push to two green checks: deterministic tests 3–5 min, then Astra/high 2–3 min. That holds while a maintainer machine runs the watcher. An automatic correction adds about 5 minutes. A human only acts at the start (work order, PR) and at the end (merge decision).
- Benefit shown today: the reviewer found every planted defect without false positives, answered a human question with evidence, and the correction loop fixed a defect without a human. The factory also blocked a policy change until a human decided.

Where the factory can create more work than it saves, and the counter-measure:

| Risk | Counter-measure |
|---|---|
| PRs wait because nobody runs a reviewer | Run one review loop per working day (README: "Alle wartenden PRs prüfen"). The `awaiting-senior-review` label shows the queue. |
| Every merge invalidates all open PRs | Keep at most 2–3 PRs open, merge promptly, avoid long-lived branches. |
| A new work order needs its own PR first | Write one work order per feature, not per commit. Its `allowed_paths` can cover several follow-up PRs. |
| A reviewer or model glitch blocks a PR | Retry once (`gh workflow run factory.yml -f pr=<n> -f retry=true`). If it stays stuck, use the maintainer bypass with a reason comment. |
| Pointless or oversized PRs | The work order and the human merge decision filter them; the reviewer only gives P2 hints. Split anything over 40 files or about 780 KB of review material. |

Verdict: it is usable if PRs stay small and a review loop runs during working hours. Without that discipline the waiting time and re-reviews outweigh the benefit.
